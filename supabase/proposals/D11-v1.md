Separately, a single1500-paise payment allocated500+1000 to two purchases cannot use one allocation row keyed only by the payment operation ID; treating each allocation as a payment can double-debit cash. Deleting the account must remove allocations before their restricted purchase parents without deleting unrelated users.

## Exact proposed approval text

Approve D11-v1 as a scoped schema supplement to PRD20 and32, with the following requirements:

1. Identity and ownership. public.users.id references auth.users(id) ON DELETE CASCADE. financial_profiles.user_id is unique. Every user-owned row has a non-null user_id referencing public.users(id) ON DELETE CASCADE, and referenced parents expose UNIQUE(user_id,id). Every child-parent reference includes user_id in a composite foreign key, including cycle/bucket/purchase/payment/goal/operation references. Request payloads cannot supply user_id; derive it from verified Supabase authentication and auth.uid() inside the database. Reject missing or anonymous authentication and never authorize through editable user metadata.

2. Accounting structure. Preserve the original logical entities and add explicit pay_cycles, cycle_buckets, ledger_adjustments, goal_reservations, operation_log and card_payment_allocations as required by the approved accounting model. Store money as checked BIGINT paise, financial dates as DATE, and instants as TIMESTAMPTZ with explicit Asia/Kolkata date conversion. Track cycle income separately from baseline, cycle contributions separately from held goal reserves, carried commitments separately from new commitments, explicit opening cash/confirmed inflows/cash outflows/residual drift and exact revisions. CC_accrued derives from outstanding tracked purchases and allocation rows across cycles, never a freely editable client balance. Do not invent rules for an unresolved source decision merely because its future data field exists.

3. Mutation boundary and table policies. Enable and FORCE RLS on every user-owned table. Grant authenticated users SELECT only where needed, with auth.uid()=user_id (users.id for users) and a non-anonymous authenticated context. Deny all anonymous table access. Revoke direct client INSERT/UPDATE/DELETE/TRUNCATE and default function EXECUTE grants. Financial writes occur only through narrowly scoped per-user transactional functions; no service-role client for normal operations. Where a definer is needed to prevent direct-table bypass, its owner is a dedicated NOLOGIN/NOBYPASSRLS/non-superuser role which does not own the tables, has only required grants, and is not granted to client roles. It remains subject to RLS USING/WITH CHECK predicates for the verified caller. Functions use a fixed safe search_path, fully qualified objects, explicit identity/ownership/argument checks, and specific EXECUTE grants. Private implementations are outside exposed API schemas; reviewed public invoker wrappers are the only API entry points. No public helper grants or client-settable bypass flag.

4. Stable operations and concurrency. operation_log is keyed by(user_id,operation_id), with operation kind, versioned canonical request fingerprint and canonical replay result. One UUIDv4 identifies one intent across retries. Changed body/kind for the same ID returns REPLAY_MISMATCH; identical committed replay returns the original result before checking current revision. All mutations for a user serialize on a common user-row lock, then lock child rows in fixed order. Validate expected revision after acquiring the lock; stale new operations return VERSION_CONFLICT. Use the existing OPERATION_IN_PROGRESS retryable result for bounded lock-wait contention. The operation record, financial changes, revision and replay response commit in the same database transaction. A failure leaves none of them committed; a retry uses the same ID. Do not persist an abandoned in-progress row outside that transaction.

5. Transactions and payment allocations. Cash/UPI/debit manual spend inserts one current-cycle transaction, increments the named cycle bucket and aggregate spent, and debits cash once in the same transaction; card purchases use the separate approved reserve effects when their later slice is implemented. A card payment has one header/stable operation and total cash debit, with one or more allocation rows linking same-user tracked purchases. Allocation amounts are positive, totals match the tracked header amount, and outstanding limits are revalidated under locks. Mixed legacy/tracked payments carry explicit legacy-obligation and tracked-purchase allocations under one cash-debit operation. Settlements never create a discretionary debit or overlap O_unpaid. No payment feature is exposed until its full lifecycle tests pass.

6. Deletion and history. Account-owned FK paths cascade from auth.users through public.users. Keep individual bucket->transaction and purchase->allocation deletion protection using same-user composite ON DELETE NO ACTION DEFERRABLE INITIALLY IMMEDIATE references; defer only these named constraints inside the privileged account-purge transaction. At its end, all owned dependent rows must be gone, so account cascades cannot leave dangling references. This replaces RESTRICT only to allow complete account purge; ordinary referenced-parent deletion remains prohibited. Client roles have no delete grants. The purge removes allocations/headers, transactions including raw text, adjustments/reservations, replay results, cycles/buckets, profile and app user; all later user-owned tables join the tested purge graph. Auth deletion/session termination is separately verified in its authorized slice, never claimed from cascades alone. No archive, retention or historical-edit exception is created by D11.

7. Scope of approval. D11 approves schema/security/atomicity structure only. D05-extension, D07-card/funding, D08–D10, D12–D26 remain independently OPEN; in particular D17 must resolve how declared onboarding budget persists and D22 how drift affects budget. Do not implement those semantics or claim PH-11 complete based on D11 approval alone. Prepare/test locally before any separately authorized remote application. Frozen PRD remains unchanged.

## Table and foreign-key plan

| Table | Owner / key and parents | Purpose / important constraint |
| --- | --- | --- |
| users | id -> auth.users CASCADE | verified identity, stored health/onboarding progress, common lock root |
| financial_profiles | unique user_id -> users CASCADE | baseline/anchor, revision; no caller identity |
| pay_cycles |(user_id,id); owner CASCADE | explicit start/expected payday, confirmation state, opening cash and cycle budget inputs; one active cycle/user |
| obligations |(user_id,id); owner CASCADE | configured mandatory/legacy-only commitments |
| cycle_obligations |(user_id,cycle_id,obligation_id), composite parents | due/paid amounts per cycle without erasing history |
| buckets / cycle_buckets | owner, composite cycle and bucket parents | bucket configuration vs per-cycle allowance/spent/floor snapshots |
| transactions | owner + same-user cycle and cycle-bucket | active-cycle spend facts; parent protection for individual deletion |
| operation_log |(user_id,operation_id); owner CASCADE | kind/fingerprint/result/revision; no raw input text/payee duplication or analytics logging |
| ledger_adjustments | owner + operation/cycle | one cash delta/ residual drift event; full drift remains reconciliation audit metadata |
| goals / goal_reservations | owner + same-user goal/cycle/operation | held and cycle contribution history; no new goal execution semantics |
| card_liability_payments | owner + operation/current payment cycle | payment header total; stable ID, original date preserved |
| card_payment_allocations | owner + same-user header/purchase | per-purchase release; positive amount, unique(header,purchase), locked aggregate limit |
| obligation_payment_allocations | owner + operation/cycle obligation | explicit legacy portion of a mixed payment; one shared cash debit |
| next_cycle_commitments / reconciliations / recovery_plans | owner + relevant same-user cycle/operation | retain PRD facts; later mutation rules independently gated |

All FK leading columns indexed. Lifecycle tables can be introduced in later migrations of the approved plan; PH-11 needs only its active approved slice, not speculative mutation functions for all entities.

## Transaction review sequence (not implemented)

Onboarding: verify identity and bounded input -> create/lock own app user -> replay lookup -> expected revision/profile-existence validation -> create profile/cycle/obligations/starter buckets under D17-approved initialization -> exact canonical calculation -> store revision/result -> commit. Duplicate operation returns the same IDs; forced failure removes partial user/profile/child rows and replay claim.

Manual spend: verify identity -> lock own app user -> replay comparison -> lock active cycle and same-user bucket -> validate current date, amount, method, expected revision and applicable source decisions -> insert transaction -> update cycle bucket/ledger once -> canonical recalculation -> store revision/replay response -> commit. On a forced intermediate failure, transaction/bucket/cash/revision/replay row all roll back. Same-ID concurrent calls yield one write; distinct IDs at the same expected revision yield one success and one conflict; fresh revision retry can then succeed.

Remaining decision examples: D17 onboarding250000paise declared minus50000 unpaid initially gives200000; subsequent10000 cash spend must not silently switch to a salary-derived pool. D26 factual spend above available declared cash needs its own decision; D11 does not define rejection/reconciliation behavior. D10 timing/undo and D20 bucket history likewise remain separate.
